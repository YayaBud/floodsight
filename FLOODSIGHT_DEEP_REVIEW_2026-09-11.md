## A. Executive summary

**Overall system health: the application cannot complete a single simulation end to end.** This is not an accuracy degradation; it is a hard break in the run path, introduced by the uncommitted remediation itself. Everything downstream of `POST /api/run` — status, results, snapshots, roads, exports, validation — returns 404 or stays permanently `queued`. The system worked before this pass (`findings_results.md` records a verified end-to-end run, job `8d026d4f`, 2026-09-04). It does not work now.

Underneath that, the deeper pattern is consistent: **FloodSight's numerics are considerably better than its inputs, and its presentation layer is considerably more confident than either.** The 2D solver is a genuine well-balanced Audusse / MUSCL / SSP-RK2 scheme with an explicit mass ledger. What is fed into it — reservoir geometry, breach location, initial water level — is asserted from a table rather than derived from terrain, and where the terrain refuses to cooperate the pipeline edits the terrain. What is drawn on top of it — reservoir polygon, river channel, dam axis, the "Delft3D" benchmark, the shelters, the historical arrival windows — is in several measured cases hand-authored in JavaScript and demonstrably inconsistent with the DEM the solver actually ran on.

**Biggest technical risk.** The run path is broken in two independent places at once (FS-01, FS-02), and 0 of 125 archived runs carry the manifest the new API requires (FS-03). Restoring service needs both a code fix and a decision about the 125 legacy runs.

**Biggest physics risk.** The Annamayya reservoir is initialised to 206.0 m — **3.6 m above the highest point of the DEM barrier it is supposed to sit behind** (measured 202.4 m). The start state already overtops the terrain along the whole axis, so the flood is not a consequence of the breach (FS-04). Compounding it, the Copernicus DSM flattens the reservoir to a constant 192.50 m plane with no bathymetry while the scenario asserts a 180.0 m bed, so roughly 12.5 m of the claimed storage does not exist in the terrain (FS-05); the pipeline restores connectivity by carving a 130 m trench into the DEM and hard-lowering one cell at a hardcoded coordinate (FS-07, FS-08).

**Biggest data risk.** Four artefacts present computed or authored values as observation. The "Delft3D-FLOW" benchmark curve is the Ritter analytical solution relabelled, with a ±0.14 m band generated by `h_analytical.map(h => h + 0.14)` (FS-15) — and the SIH statement names the SPH-vs-Delft3D comparison as a deliverable. `malpasset_benchmark.json` ships a `simulated_wse_m` next to every `measured_wse_m`, and the directory's own README states those measurements were *not recovered* (FS-46). The Annamayya "observed" flood extent is a single unattributed polygon with a float64 coordinate signature (FS-17). The historical arrival windows that `compare_arrivals.py` deliberately withdrew are still painted on the timeline by `spine.js` (FS-19).

**Biggest performance risk.** A run load fetches **7.0 MB of GeoJSON across 78 frames up front**, plus 4.0 MB of preview PNGs and a single 2.1 MB / 5,299-feature roads file — all measured on `data/scenarios/af1829c6`. Each playback tick hands MapLibre a fresh GeoJSON object, re-serialising and re-tiling the full polygon set every 2 s (FS-33 – FS-35).

**Biggest architectural risk.** The generalisation work exists but is not connected. `event_graph.py` — the compound-event engine the SIH statement requires — is reachable only from its own test. `src/scenarios.py` hardcodes `validated: False`, and `data/geometry/`, which its validator requires, does not exist, so **every** scenario reports `hydraulic_ready: False`. `src/observation_manifest.py` enforces a strict provenance contract against `data/observations/`, which also does not exist, while the loader actually in use bypasses it entirely (FS-49). Scenario truth is duplicated across 23 locations with measurable divergences (FS-20 – FS-22).

### What is sound, and should not be touched

- `src/m4_solvers/swe_2d.py` — Audusse hydrostatic reconstruction, MUSCL + minmod, SSP-RK2, Rusanov flux, point-implicit friction, Kurganov-Petrova desingularisation, and an injected / stored / outflow / clipped mass ledger. The docstring's account of why the previous scheme was replaced (20 m/s spurious currents, 39 m surface drift, 31.5 % mass error) is serious engineering.
- The active-window optimisation, recorded in `memory.md` as bit-exact and asserted with `==` in `tests/test_swe_active_window.py`.
- `src/run_manifest.py` **as a design**: content-hashed, atomic writes, path-escape checks, explicit status transitions, fail-closed `is_valid`. The defect is that nothing populates it, not the module.
- The Derna validation chain against Copernicus EMSR696 (1,843 real observed polygons on disk), and the documented decision in `memory.md` not to close the Bias gap by adding rainfall-runoff.
- All 7 DEMs are in the correct per-scenario UTM zone at ~25–30 m, with consistent nodata. The CRS discipline in `fetch_dem` / `_validate_cached_dem` is good.

## D. Physics audit

### Does the current system represent physical flood propagation?

**The routing does. The generation does not.**

**What is genuinely physical.** `src/m4_solvers/swe_2d.py` solves the 2-D Saint-Venant equations with Audusse hydrostatic reconstruction, so the pressure gradient and bed-slope source cancel exactly at rest; MUSCL with a minmod limiter on free surface and primitive velocities; SSP-RK2 in time; a Rusanov flux; point-implicit friction that stays stable in thin films; and Kurganov-Petrova desingularisation for velocity recovery near zero depth. It tracks injected, stored, boundary-outflow and positivity-clipped volume and reports closure rather than assuming it. `tests/test_swe_validation.py` and `tests/test_ritter.py` exercise lake-at-rest and the Ritter analytical dam break. Once water is in the domain, its motion over the terrain is credible.

**Where the water comes from, traced end to end.**

1. `simulate_generic_cascade` (`cascade.py:177`) is a **0-D reservoir** with a Muskingum 1-D inflow: a triangular upstream pulse, routed by `k_s`/`x`, plus a Gaussian catchment-runoff term, integrated against a power-law stage-storage `V = α·h^2.5`, discharging through a weir spillway and a growing trapezoidal breach.
2. The breach opening grows as `frac = min(1, (t/t_f)^1.2)` and the invert erodes as `z_inv = z_crest − (z_crest − z_bed)·frac^0.8` (`cascade.py:290-292`). **Neither exponent carries a citation.** Breach discharge is then clamped at `q_p_env × 1.15` (`:295`) — a 15 % headroom over the empirical envelope, also uncited.
3. The resulting Q(t) is injected into the 2-D solver at **one cell**, spread over a 5×5 Gaussian kernel (`swe_2d.py:672-678`).
4. The 2-D domain **starts dry** (FS-09). There is no reservoir in it, no drawdown, and therefore no feedback from the 2-D state back to the reservoir.

This is a legitimate architecture — a 1-D storage model coupled to 2-D routing by a discharge boundary — and it is how many operational dam-break tools work. The defect is not the architecture; it is that the system never says so, and that four separate properties of the coupling are wrong:

- **The initial condition overtops the terrain.** `wse_m = 206.0` against a DEM barrier topping out at **202.4 m** (FS-04). Whatever the breach does, the reservoir is already above the divide.
- **The injection point is inside the reservoir**, ~545 m upstream of the barrier, at DEM elevation 192.50 m (FS-06). Injected water must first traverse the carved trench.
- **The terrain is edited to make the flow possible** — a 130 m corridor carved to invert 180–185 m, plus one cell lowered to 176.0 m at a hardcoded coordinate (FS-07, FS-08). Carving is a standard conditioning technique; doing it without recording the carved volume or exposing it as provenance is not.
- **Storage is asserted, not measured.** 63.43 MCM at FRL is a table value; the DEM offers a flat 192.50 m pool with no bathymetry (FS-05). The two are never reconciled, and when DEM stage-storage is rejected the fallback to the table value is not labelled in the output (FS-29).

### Physics acceptance conditions before operational use

1. Initial reservoir level ≤ the DEM's own impounding crest along the dam axis, or the barrier explicitly raised to a surveyed crest with provenance recorded.
2. DEM-derived storage at FRL within a stated tolerance of the scenario's stage-storage curve, or the discrepancy published as a known bias.
3. Carved volume reported per run; a run that carves more than a declared budget fails.
4. Breach-growth exponents (1.2, 0.8) and the 1.15 discharge headroom either cited or replaced with a cited erosion model.
5. Mass closure reported in the API payload, not only in a log line.

## H. Compound-event architecture

`event_graph.py` already implements most of what is needed — node validation, cycle rejection, forcing, routing, stage — and is used by nothing (FS-20). The current executable path is a fixed two-node chain hard-coded into the `cascade` dict shape: one upstream pulse, one Muskingum reach, one reservoir, one breach.

**Proposed model.** A scenario is a directed acyclic graph.

```
Node kinds:  SOURCE        upstream pulse, rainfall-runoff, glacier/lake outburst
             STORAGE       reservoir, natural impoundment, moraine lake
             STRUCTURE     dam, ring bund, barrage, landslide blockage
             REACH         routed channel segment (Muskingum, K and x)
             JUNCTION      tributary confluence
             SINK          2-D domain inflow boundary

Edge:        {source, target, transport: "routing"|"instant", lag_s, loss}

Execution:   topological sort -> integrate each node on a shared time axis
             -> a STRUCTURE failing emits a breach hydrograph into its outgoing edges
             -> a STORAGE integrates inflow - spill - breach against its stage-storage
             -> SINK nodes become 2-D solver inflow points (plural, not one)
```

This covers all five shapes §14 asks for without special cases:

- **Single** — SOURCE → STORAGE → STRUCTURE → SINK.
- **Sequential (Annamayya)** — Pincha STRUCTURE → REACH(34 km, K=7200 s) → Annamayya STORAGE → Annamayya STRUCTURE → SINK. This is what the current `cascade` dict encodes; the graph just makes it declarative.
- **Parallel** — two SOURCEs (rainfall runoff + reservoir release) into one JUNCTION.
- **Cascading (South Lhonak)** — landslide STRUCTURE → moraine STORAGE → STRUCTURE → REACH(42 km) → Chungthang STORAGE → STRUCTURE → SINK. **This also fixes FS-43**, where one scenario key currently holds two incompatible structures.
- **Multiple failures** — N STRUCTUREs whose REACHes converge on one JUNCTION.

**Critical constraint the current 2-D coupling cannot meet:** multiple SINK nodes. `run_2d_swe_simulation` takes a single `inflow_x_idx`/`inflow_y_idx`. Parallel and multi-failure scenarios need a list of inflow cells with independent hydrographs. That is a contained change to the inflow-kernel block (`swe_2d.py:672-728`) and is a prerequisite for §14, not an optional extra.

**Migration.** Keep the `cascade` dict as a compatibility shim by finishing `cascade_config_to_graph` (`cascade.py:582`) — it already exists and is uncalled — then route `run_pipeline` through `simulate_event_graph`. Delete `simulate_annamayya_cascade` and its 28-line duplicate config at the same time.

**Node kinds today, precisely.** `event_graph.py:57` validates only `node.get("type") in {"forcing", "reservoir"}` — `STRUCTURE`, `REACH`, `JUNCTION` and `SINK` above are the proposed vocabulary, not yet in the code. The `reservoir` node's breach sub-block is mechanism-agnostic, a single linear-ramp weir model applied regardless of cause. See §P for the taxonomy `STRUCTURE` needs before it can mean what this section's examples require, and see §O for why the migration above cannot be pure wiring — its target breach kernel disagrees with the live one (FS-55).

## I. Time model redesign

There are currently **four** independent notions of time, and no mapping between them:

1. **Solver time** — seconds from the start of the 2-D solve, `t=0` at breach.
2. **Cascade time** — seconds relative to the downstream failure; the upstream event sits at `−lead_time_s`. Pre-breach frames get negative `t_min`.
3. **Event clock** — a wall-clock origin hardcoded in three places: `scenarios.py:113` (`2021-11-19T05:45:00+05:30`), `SCENARIO_DAMS.annamayya.event_clock` (`map.js:293`), and the event list in `spine.js:131`.
4. **Display time** — `T+n min` strings, formatted three different ways (`fmtMin`, `setRow`, `fmtT`); only `fmtT` handles negatives, so pre-breach pins render as **"T+-150 min"** in `ui.js:96`.

`scenarios.py:114` even records the contradiction in a string: *"Review records unresolved 03:30 local report versus T-150 simulation clock."* The upstream failure is `03:30` in `data_fetcher.py:411` and `03:15` in `map.js:296` and `map.js:300`. Both cannot be right.

**Proposed model.**

```
EventClock:   origin_iso        ISO-8601 with offset, ONE definition per scenario
              origin_anchor     which physical event t=0 means
                                 (breach_initiation | overtopping_start | first_failure)
              classification    OBSERVED | RECONSTRUCTED | ASSUMED
              source            citation
              uncertainty_s     +/- on the origin

SimClock:     t_s relative to origin_anchor; may be negative
              every frame, event, arrival and cut time carries t_s ONLY

Timeline:     [{id, t_s, t_uncertainty_s, label, classification, source, node_id}]
              produced by the event graph, served by the API, never authored in JS
```

Rules that follow, each of which fixes a defect above:

- **One origin per scenario, server-side.** The frontend never contains a timestamp (fixes the 03:15/03:30 split and FS-22).
- **`t=0` is not universally "breach".** `origin_anchor` names it, so a GLOF or a blockage scenario can anchor where it makes sense (§13).
- **Wall-clock is a render-time transform** of `t_s` through the event clock, computed in one function, which handles negatives (fixes "T+-150 min").
- **Every timeline entry carries its classification and source.** An observed arrival and a modelled one must never render identically (fixes FS-19).
- **The timeline comes from the graph.** With §H in place, node failure times *are* the timeline, so a scenario cannot have a timeline that disagrees with its physics.

**Relation to lake-state classification (§O).** `EventClock.classification` above (`OBSERVED | RECONSTRUCTED | ASSUMED`) is the event-timing instance of §G's six-way provenance vocabulary. §O adds a fourth value, `ROUTED`, for the specific case of a water level produced by integrating a node's own inflow/storage/outflow equations rather than asserted or fraction-filled — the same distinction this section needs wherever `t=0` is the output of a computed trigger (§O, §P) rather than a scenario constant.

5. **Nothing is ever torn down.** Zero `removeSource`/`removeLayer` calls, so switching scenarios accumulates the previous scenario's data in live sources.

| Change | Mechanism |

| Frame streaming | Fetch a window of ±N frames around the playhead; bounded LRU; prefetch by playback direction |

## O. Dynamic impoundment and lake-formation state model (addendum, 2026-09-11)

This section and §P below respond to two requirements supplied after the initial review pass, same day. Method is unchanged from the rest of this document: read-only, evidence-first, `NOT_IMPLEMENTED` / `UNKNOWN` where the code does not support a claim rather than filling the gap.

**Requirement, paraphrased.** Pre-breach lake frames must be the output of a state evolution — blockage → inflow → storage → level → overtopping/failure criterion → breach → outflow → downstream routing — not arbitrary fill fractions or invented timestamps, with every frame tagged `ROUTED` / `OBSERVED` / `RECONSTRUCTED` / `ASSUMED` and no fabricated lake presented as history.

### What already does this, verified

Two building blocks already implement the physically-correct version of this pipeline, for the scenarios that reach them:

- **`build_stage_storage`** (`src/m2_geometry/fill.py:49`) computes a genuine stage-storage curve — `stage_curve_h`, `stage_curve_V`, `stage_curve_A` — by seeded connected-component flood-fill from `z_min` to `wse_m` in 100 steps (`fill.py:136-144`), not an assumed formula. This is the "explicit stage-storage relationship" the requirement asks for, and it is DEM-derived, not invented.
- **`simulate_prebreach_rise`** (`src/m3_breach/cascade.py:387`) is a real inflow→storage→level→outflow integrator for the pre-breach phase: a Muskingum-routed upstream pulse plus a Gaussian catchment term (`cascade.py:428-448`) drive continuity against the reservoir's own storage, with a gated spillway release (`:483-489` — pass inflow while `z ≤ FRL`, rating-curve discharge above it). Storage, level and outflow are consistent by construction; this is not a fill-fraction animation.
- **`compute_lake_depth_grids(..., levels_m=pb_levels)`** (`fill.py:192`, called at `run_pipeline.py:823-832`) renders that routed trajectory — sampled to 6–8 frames — into depth grids. For the scenarios that reach this path, pre-breach lake growth already **is** derived from state evolution, confirming FS-11's "half-fixed" verdict.

### Where it stops

- **Only scenarios with a `cascade` config block reach `simulate_prebreach_rise`.** Every other scenario falls through the `else` branch at `run_pipeline.py:834-836`: `lake_fractions = (0.25, 0.50, 0.75, 0.95)` at invented `lake_dt_mins = [-120, -60, -30, -10]` (FS-11, unchanged). No inflow hydrograph is constructed for these scenarios at all before breach — there is nothing to route.
- **The two stage-storage representations never meet.** The cascade path's reservoir (`cascade.py:253-257`, `elev_from_v`/`v_from_elev`) is pure algebra — `V = α·h^exp`, fit to one FRL/volume pair from the scenario table — and never touches the DEM. `build_stage_storage`'s DEM-integrated curve runs only on the non-cascade path (`run_pipeline.py:516-520`). FS-05's 12.5 m storage gap at Annamayya is exactly this: the cascade reservoir that actually drives the hydrograph has never been checked against the terrain it claims to sit in.
- **The overtopping/failure criterion is evaluated in the one module nothing calls.** `event_graph.py:234-235` searches for the first interval where `stage ≥ overtopping_elevation_m` and sets `actual_trigger` there — a real, computed initiation condition. The live path does not do this: `simulate_prebreach_rise` and `simulate_generic_cascade` are two separately-authored regimes glued at a scenario-asserted `t=0` (`run_pipeline.py:392`, `wse_m = cascade_cfg["reservoir"]["z_crest_m"]` fed straight in as the post-breach initial condition). "Determine overtopping/failure from scenario conditions where possible" is met in the disconnected module (FS-20) and not in the one that runs.
- **Progressive failure exists, but as two disagreeing models (FS-55).** `cascade.py:290-292` ramps breach width as `frac = (t/t_f)^1.2` with invert erosion `frac^0.8`, discharge capped at `1.15 × q_p_env` (`:295`), coefficients uncited (already noted in §D). `event_graph.py:238-241` ramps width **linearly** in `elapsed/formation` against a weir coefficient defaulting to `1.7`, not `0.85`. Both are "the generic breach"; neither is selected by mechanism (§P); and because `cascade_config_to_graph` (`cascade.py:582`) maps a scenario's `cascade` block into `event_graph.py`'s schema, finishing that bridge as §M/P2-1 recommends would silently swap one breach kernel for the other for every existing cascade scenario. That migration needs a reconciliation step, not just a wire-up.
- **No classification field exists in the output.** FS-11's own proposed fix — tag every lake frame `level_source` — is not implemented; `compute_lake_depth_grids`'s return dict (`fill.py:273-279`, `:294-300`) carries `fraction`, `level_m`, `volume_m3`, `area_m2`, `depth_grid` and nothing that says how the level was obtained.

### Proposed state model

Adopt a four-way classification specific to water-level state, nested under §G's existing six-way provenance vocabulary rather than competing with it (`ROUTED` and `ASSUMED` are the two ways §G's `MODELED` can arise for a lake level; `OBSERVED`/`RECONSTRUCTED` keep their §G meaning):

```
LakeState (per timestep, per STORAGE node — see §H/§P for STORAGE/STRUCTURE):
  t_s
  inflow_m3s            float
  storage_m3            float, from stage_storage, never asserted
  level_m               float
  outflow_m3s           {spillway, breach, seepage: NOT_IMPLEMENTED}
  freeboard_m           crest_elevation_m - level_m
  failure_state         INTACT | OVERTOPPING | BREACHING | BREACHED
  classification        ROUTED | OBSERVED | RECONSTRUCTED | ASSUMED
  source                citation

StageStorageCurve (per STORAGE node, one per run):
  source                DEM_FILL | ANALYTICAL_POWER_LAW | SURVEYED
  h[], V[], A[]
  classification
  reconciliation_gap_m3 |null   populated when DEM_FILL and ANALYTICAL_POWER_LAW both exist and disagree (closes FS-05's silence)
```

`classification` definitions for this vocabulary: `ROUTED` — produced by integrating the node's own inflow/storage/level/outflow equations (`simulate_prebreach_rise`, once extended to every scenario); `OBSERVED` — from a gauge or satellite lake-level record (`NOT_AVAILABLE` for all 7 scenarios today — no such record is on disk, consistent with §G); `RECONSTRUCTED` — derived from a documented post-event survey of maximum extent; `ASSUMED` — a parameterized fraction/time not backed by integration, today's non-cascade fallback. A frame must never render `ASSUMED` identically to `ROUTED` (the general rule already stated in the Provenance row above).

### Explicitly `NOT_IMPLEMENTED`, rather than silently faked

- Seepage/piping loss term in reservoir continuity — absent from both `simulate_generic_cascade` and `simulate_prebreach_rise`.
- Multi-inflow lake state for parallel/multi-failure graphs — the 2-D solver takes one inflow point (§H); a lake fed by two blockages cannot be represented.
- Bathymetric correction reconciling a DEM-flattened reservoir with its stage-storage curve — scoped already as P0-2.
- Observed lake-level time series for any scenario — none exists on disk.

### Acceptance conditions

1. Every executable scenario reaches an inflow→storage→level→outflow integrator before breach, not only scenarios with a `cascade` block.
2. Exactly one stage-storage curve per STORAGE node, DEM-derived where possible, with the analytical power law surviving only as a documented, provenance-tagged fallback (mirrors the existing `except Exception` pattern at `run_pipeline.py:533-540`).
3. Overtopping/failure trigger is computed from `level ≥ crest` (or the mechanism-specific criterion in §P), never asserted as a scenario constant.
4. Every lake-formation frame carries `classification` and `source`; no `ASSUMED` frame is visually indistinguishable from a `ROUTED` one.
5. The two breach-growth kernels (FS-55) are reconciled — one retained per mechanism (§P), not one retained by accident of which function is called.

## P. Failure-mechanism taxonomy

**Requirement, paraphrased.** Represent `failure_mechanism` as a first-class, per-STRUCTURE attribute across a defined taxonomy, each capable of influencing initiation condition, timing, breach geometry evolution and outflow hydrograph — not a label, and not silently routed through one generic breach equation. Mark mechanisms without a physically justified implementation `NOT_IMPLEMENTED`.

### Current state

The only structured mechanism signal in the repository is the API's

```
failure_mode: Literal["overtopping", "piping", "instantaneous", "breach"]   # main.py:202
dam_type: Optional[str]                                                     # main.py:208
```

validated at `main.py:294-295` and threaded through `worker.py:23,27` into `run_pipeline.py:543-549`'s `DamGeometry(failure_mode=..., dam_type=...)` — but **only on the non-cascade, single-structure path** (`run_pipeline.py:505-549`). `simulate_generic_cascade` (`cascade.py:177`) takes `(cfg, total_duration_s, dt_s, breach_tier)` — no mechanism parameter of any kind. **FS-56: Annamayya and South Lhonak — the repository's only two compound-event scenarios, and precisely the shapes this requirement's own examples #1 and #2 describe — cannot express a failure mechanism at all.** Every non-compound scenario gets a four-value, mostly-binary mechanism; every compound scenario gets none.

Where `failure_mode`/`dam_type` do reach physics, the reach is thin:

- `froehlich.py:35-36` — `k_o = 1.4 if dam.failure_mode == "overtopping" else 1.0; Z = 1.0 if ... else 0.7`. Every one of `piping`, `instantaneous`, `breach`, or any future value collapses onto the same `else`.
- `von_thun.py:54-56` — the same binary split, for the formation-time formula only.
- `macdonald.py`, via `dam_type` — an "engineering override" on width and `Q_p` that never reaches `formation_time_h` (FS-52, already an open test failure: the override is inconsistent with itself before it is even inconsistent across mechanisms).
- `event_graph.py`'s `reservoir` node (FS-20, disconnected) has no mechanism field either — its breach sub-config (linear width ramp, §O) applies identically regardless of cause.

Scenario data already narrates distinct mechanisms in free text that no code reads:

| Scenario | Structure | `status` / `trigger` text (verbatim) | Implied mechanism | Physics actually applied |
|---|---|---|---|---|
| Annamayya | Pincha ring bund (upstream) | *"Overtopped & ring bund washed out"* (`data_fetcher.py:411`) | Overtopping erosion / washout | Generic Muskingum pulse into the reach (`generate_pincha_outflow`) — mechanism-agnostic by construction |
| Annamayya | Annamayya dam (downstream) | *"Overtopped & earthen bund washed out"* (`:419`) | Overtopping → progressive embankment breach | `simulate_generic_cascade`'s single trapezoidal kernel — same kernel regardless of mechanism |
| South Lhonak | Moraine / ice-rock blockage (upstream) | *"Ice-rock avalanche into proglacial lake causing moraine dam overtopping"* (`:310`) | Landslide-induced overtopping / GLOF outburst | Asserted directly as `upstream.peak_q_m3s: 20000.0` (`:332`) — no landslide-impulse or moraine-breach model computes it |
| South Lhonak | Chungthang dam (downstream) | *"Completely washed away within 10 min of surge arrival"* (`:318`) | Surge-induced structural failure — **not overtopping**, the reservoir did not rise, a wave hit it | The same `simulate_generic_cascade` trapezoidal kernel, indistinguishable from the upstream node's |

South Lhonak already carries two structures with two different mechanisms under one scenario key and one breach kernel — this is FS-43 (§H), restated in mechanism terms rather than node-count terms.

### Proposed schema

Attach to the STRUCTURE node once §H's node kinds exist (today, `event_graph.py:57` recognises only `{"forcing", "reservoir"}` — there is no `STRUCTURE` type to attach this to yet; until then, attach to the `dam_body`/`dam_axis` geometry feature via `scenarios.py:56`'s `valid_roles`, which already carries `classification`/`source` per feature and is the nearest existing home):

```
STRUCTURE.failure_mechanism          enum, see taxonomy below
STRUCTURE.failure_trigger            free-text citation of the physical cause
STRUCTURE.failure_start              t_s, or null before initiation — same axis as §O's failure_state
STRUCTURE.failure_duration           breach/erosion formation time, seconds
STRUCTURE.breach_parameters          {model: <named equation>, ...params}
STRUCTURE.parameter_source           citation
STRUCTURE.parameter_classification   OBSERVED | OFFICIAL_ESTIMATE | RECONSTRUCTION | MODEL_RECONSTRUCTION | ASSUMED
STRUCTURE.uncertainty                per-parameter +/- or named ensemble spread
```

`scenarios.get_scenario_manifest()` (`scenarios.py:86`) is the natural place to surface this: it already returns a per-scenario manifest with a `_field_provenance` classifier (`:72-83`) of the right shape. Add a `structures: [...]` array, one entry per STRUCTURE, carrying the eight fields above verbatim — additive to the existing return shape, not a rewrite.

### Mechanism → implementation status

Honest per the requirement's own instruction: mark `NOT_IMPLEMENTED` rather than silently defaulting.
